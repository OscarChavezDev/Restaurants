El sistema principal

Restaurants administra el ciclo completo de un restaurante: catálogo y menús, reservas con pre-pedido, promociones, pagos con comprobante, distribución de mesas y un dashboard por rol (cliente, dueño, admin). Arquitectura hexagonal en el backend, para que la integración con otros sistemas entre por un solo borde limpio (infrastructure/) sin filtrarse al dominio.

Lo que exponemos

Restaurants actúa como proveedor para el resto del ecosistema: otros sistemas externos (hoteles, eventos, transporte) consumen datos y acciones nuestras a través de dos superficies, cada una con su propio nivel de acceso — desde autenticación propia de cada dueño hasta acceso de sistema a sistema.

Portal de desarrolladorAPI keys propias

Para lo que sí necesita identificar a alguien, hay autoservicio de claves (/v1/developer/api-keys): cualquier dueño o developer genera, revoca o regenera su propia clave desde el dashboard, sin pedirle nada a un administrador. La pieza que lo hace funcionar es el filtro de autenticación: no asigna un rol fijo de "sistema" a quien usa una key, carga al usuario real que hay detrás de ella, con sus roles reales. Eso significa que cualquier endpoint que ya esté protegido por rol de dueño sigue funcionando igual con una API key, sin escribir permisos nuevos por cada caso.

ApiKeyAuthenticationFilter.java
Optional<ApiKey> apiKey = apiKeyService.validateAndTouch(rawKey);
if (apiKey.isPresent()) {
    // carga al DUEÑO REAL de la key — con sus roles reales,
    // no un rol fijo de "sistema". Por eso OwnershipGuard funciona igual.
    UserDetails userDetails = userDetailsService.loadUserByUsername(apiKey.get().getUserId().toString());
    var auth = new UsernamePasswordAuthenticationToken(userDetails, null, userDetails.getAuthorities());
    SecurityContextHolder.getContext().setAuthentication(auth);
}

Integración de ecosistemaJWT de sistema

Un segundo nivel, para cuando quien consulta no es una persona sino otro sistema completo (rol SYSTEM_INTEGRATION). Los tres endpoints no son alternativas entre sí — son tres pasos de un mismo flujo: primero se descubre qué restaurantes hay, después se pide el perfil completo de uno puntual, y por último se pregunta si conviene recomendarlo justo ahora.

01 · DescubrirGET /restaurants

Un sistema externo (ej. un buscador de planes o actividades) todavía no sabe qué restaurante quiere — pide la lista completa (paginada) para armar su propio catálogo o buscador. Sin esto, no tendría de dónde sacar el id que necesitan los otros dos endpoints.

Devuelveun RestaurantResponse por cada restaurante activo (mismos campos que "availability", abajo)
02 · Perfil completoGET /restaurants/{id}/availability

Ya con un id puntual en mano (salido del endpoint anterior, o de una recomendación previa), se pide el detalle completo para mostrárselo a su propio usuario: una tarjeta o perfil de "este es el restaurante", con todo lo necesario para decidir si visitarlo.

Identidadnombre, categorías, rating, foto de portada
Ubicacióndirección, ciudad, región, coordenadas (lat/lng)
Operacióncapacidad total, rango de precio, horarios de la semana
Contacto del negocioemail, phone, ownerId
03 · Decisión en tiempo realGET /restaurants/{id}/daily-status

Distinto de los dos anteriores: no es el perfil (eso ya lo tiene), es la pregunta de último momento — "¿conviene recomendarlo ahora mismo?". Pensado para sistemas de itinerarios que arman un plan del día en vivo.

Horario de hoyopeningTime, closingTime, status
Capacidad ahoraavailableTables, availableSeats
Menúmenu[]: id, nombre, precio y disponibilidad por plato

Nota honesta: los primeros dos reutilizan el mismo DTO que ya usaba el dashboard del dueño (por eso el bloque de "contacto del negocio" en naranja) — nunca se pensó una respuesta angosta solo para este caso. daily-status, en cambio, sí tiene su propio DTO hecho a medida — responde justo lo que se necesita, ni más ni menos. Es el que mejor ejemplifica cómo debería ser una respuesta de integración bien pensada.

Lo que consumimos

Del otro lado, Restaurants es cliente de seis servicios externos — los seis activos en producción ahora mismo. Todos comparten la misma regla de diseño, pensada para el día en que alguno falle: si no responde o su clave deja de estar configurada, se degrada a un resultado vacío — nunca rompe la respuesta al cliente final.

El patrón, en código realisConfigured() + try/catch → null

Ejemplo real (ActifyEventsClient, Sistema de Eventos): si Actify no responde, el restaurante simplemente no muestra eventos cercanos — no hay pantalla de error para el cliente.

ActifyEventsClient.java
public EventLocation getEventLocation(String eventId) {
    if (!isConfigured()) return null;   // sin API key: ni lo intenta
    try {
        JsonNode resp = http.get().uri(baseUrl + "/events/{id}", eventId)
                .header("Authorization", "Bearer " + apiKey)
                .retrieve().body(JsonNode.class);
        // ... parsea lat/lng ...
        return result;
    } catch (Exception e) {
        log.warn("No se pudo obtener el evento {} de Actify: {}", eventId, e.getMessage());
        return null;   // degrada, no propaga
    }
}

Hospy — Sistema de Hospedajecontrato propio, no un estándar

El restaurante muestra alojamientos cercanos consumiendo la API de Hospy. Se le manda la coordenada del restaurante (lat, lng, radio en km); Hospy responde una lista de hospedajes con id, nombre, tipo, ciudad, precio desde, foto y distancia — Restaurants solo transforma esa respuesta a su propio modelo (Lodging) y la sirve tal cual en la página del restaurante. Vale la pena notar que Hospy no usa Authorization: Bearer como Actify — pide su propio header, X-Hospy-Integration-Key. Cada integración externa trae su propio contrato; el cliente se adapta al de cada quien, no al revés.

HospyLodgingClient.java
public List<Lodging> findNearby(BigDecimal lat, BigDecimal lng, double radiusKm) {
    if (!isConfigured()) return List.of();
    // ... revisa la caché de 5 min por coordenada+radio primero ...
    JsonNode resp = http.get()
            .uri(baseUrl + "/integracion/hospedajes/cercanos/?lat={lat}&lng={lng}&radio_km={r}", lat, lng, radiusKm)
            .header("X-Hospy-Integration-Key", apiKey)   // header propio de Hospy, no Bearer
            .retrieve().body(JsonNode.class);
    // ... mapea cada item a Lodging(id, name, type, city, priceFrom, photoUrl, distanceKm) ...
}

Caso real de integración fallida: correo por SMTPlección aprendida

El envío de correo usaba Gmail por SMTP tradicional. Al desplegar en Render, cada correo fallaba con Connection timed out — Render bloquea los puertos SMTP (25/465/587) en todos sus planes, sin importar que las credenciales fueran correctas. La solución fue cambiar de protocolo, no de credenciales: Resend manda por HTTPS, que sí atraviesa esa red.

ResendEmailClient.java
public void send(String to, String subject, String html, ...) {
    if (!isConfigured()) { log.warn("RESEND_API_KEY no configurada"); return; }
    var req = HttpRequest.newBuilder()
            .uri(URI.create("https://api.resend.com/emails"))   // HTTPS, no SMTP
            .header("Authorization", "Bearer " + apiKey)
            .POST(HttpRequest.BodyPublishers.ofString(mapper.writeValueAsString(body)))
            .build();
    var response = http.send(req, HttpResponse.BodyHandlers.ofString());
    // 200-299 -> log.info · si no, log.error con el motivo real (nunca lanza)
}

Extra: Sistema del Mesero

El caso de estudio completo: Meseros, un software aparte para que el mesero tome pedidos en mesa — repo distinto, base de datos distinta (Supabase), pensado para desplegarse aparte (por ahora corre en local para esta sustentación). Se integra con Restaurants solo por contrato HTTP, sin compartir código ni base de datos.

Cómo se integró

Meseros no tiene usuario ni contraseña dentro de Restaurants. El dueño del restaurante genera su propia API key desde el portal de desarrollador (la misma pieza de la sección anterior) y se la entrega a Meseros como variable de entorno. Cuando el mesero envía un pedido a cocina, Meseros llama con esa key al mismo endpoint manual que el dueño ya usaba desde su propio panel para marcar una mesa — OwnershipGuard no distingue si la llamada vino de una sesión con contraseña o de una API key, así que no hizo falta escribir ningún permiso nuevo para este caso.

LayoutController.java
@PatchMapping("/tables/{tableId}/status")
@PreAuthorize("hasAnyRole('ADMIN', 'RESTAURANTE_OWNER')")
public ResponseEntity<ApiResponse<TableResponse>> updateTableStatus(
        @PathVariable UUID restaurantId, @PathVariable UUID tableId, @RequestParam String status) {
    ownershipGuard.assertOwnsRestaurant(restaurantId); // mismo guard de siempre, sin cambios
    RestaurantTableEntity e = tableRepository.findById(tableId)
            .orElseThrow(() -> new IllegalStateException("Mesa no encontrada"));
    e.setCurrentStatus(status);
    tableRepository.save(e);
    return ResponseEntity.ok(ApiResponse.ok("Estado actualizado", toTableResponse(e, ...)));
}

Código enfocado a la integración: lado Meseros

La clave nunca toca el navegador del mesero. El cliente llama a una ruta propia de Meseros (/api/mesas/[id]/estado), y esa ruta —corriendo en su propio servidor— es la única que conoce la key y llama a Restaurants.

Meseros · src/app/api/mesas/[tableId]/estado/route.ts
export async function PATCH(request: NextRequest, { params }) {
  const apiKey = process.env.RESTAURANTS_API_KEY;      // solo servidor, nunca NEXT_PUBLIC_*
  const { occupied } = await request.json();
  const status = occupied ? "OCCUPIED" : "AVAILABLE";

  const upstream = await fetch(
    `${apiUrl}/v1/restaurants/${restaurantId}/tables/${params.tableId}/status?status=${status}`,
    { method: "PATCH", headers: { "X-API-Key": apiKey } }
  );
  return NextResponse.json(await upstream.json());
}
